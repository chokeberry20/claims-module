_Status: revision 4 (2026-11-22). Each entry gives the issue, its source (S = Functional Spec section or rule, B = Assessment Brief section) and the resolution, including the rationale._

## D-00 Precedence rule
The **spec (FRS) wins on business rules**. The **brief wins on stack, architecture, deliverables and deployment**. Where the brief adds an endpoint, field or entity the spec lacks, we add it. Real conflicts are resolved below.

| D-56 | Unit of Work semantics | B2.4, PLAN §4 | Before-commit dispatch happens inside the save and repeats up to 10 rounds. After-commit dispatch runs only after a real commit: it waits for the outer transaction and is dropped on rollback. **An after-commit failure is logged, not rethrown**, because the data is already committed. A lost GL enqueue is recovered by the **stale-Pending sweep, P3 task 27a, which is core scope**: without it, `PostingStatus` would stay Pending forever, since the D-28 retry only accepts Failed (your P2 review). `ExecuteInTransactionAsync` joins a transaction that is already open. **Retrying execution strategy (P2.5 task 17f):** with `EnableRetryOnFailure`, the explicit transaction in `UnitOfWork.ExecuteInTransactionAsync` breaks. **Verified empirically (P2 follow-up):** `BeginTransactionAsync` itself succeeds, but the **first EF operation inside the transaction** (query or SaveChanges) throws *"The configured execution strategy 'SqlServerRetryingExecutionStrategy' does not support user-initiated transactions. Use the execution strategy returned by 'DbContext.Database.CreateExecutionStrategy()' to execute all the operations in the transaction as a retriable unit."* The raw ADO command in `ClaimNumberGenerator` doesn't go through EF's strategy, so it neither throws nor retries on its own; the wrapped unit covers it. It must be wrapped in `context.Database.CreateExecutionStrategy().ExecuteAsync(...)`. A retry **replays the whole delegate**, so the replayed unit must be self-contained. Entities tracked by a failed attempt stay in the context (Added or Modified), so a naive replay would add them twice. The retried unit is therefore the whole command: a fresh scope and context per attempt, from the MediatR transaction behaviour, plus `verifySucceeded` for commit-time failures. Plain `SaveChangesAsync` outside an explicit transaction is retried by EF automatically. **Implemented (17f):** `AddPersistence` enables `EnableRetryOnFailure(5, 10 s)`. `ExecuteInTransactionAsync` runs inside the strategy and, on a replay, clears the change tracker and the collected events, so `work` must be self-contained (documented on `IUnitOfWork`). `verifySucceeded` for commit-time failures is left to P3, where the idempotency record written in the same transaction is the natural check |

## Deliberate deviations from the literal spec (summary)
- **D-19:** the aggregate limit uses the gross total (Indemnity + Expense + ALAE) instead of "across all components".
- **D-23:** ClaimAuditLog has no soft-delete or UpdatedAt columns (immutable log).
- **D-29:** the blob name adds a `{documentId}-` prefix to avoid overwrites.
- **D-13:** SLA breach is a flag, not a status (brief vs spec).
- **D-07:** the NO_CLAIMANT Critical can't be waived.
- **D-05:** request-level Criticals (BR-C-01 future loss date, BR-C-05 unknown or inactive cause code, BR-C-07 description < 20 chars) get **422 and nothing is saved**. S5.4 says Criticals leave the claim "in Draft". Only state-level Criticals (e.g. NO_CLAIMANT) are saved on a Draft claim.
- **D-24:** a user whose role can't approve at all (handler) gets **403 Forbidden**, not the **422** that S8 lists ("Your role does not have authority…"). The 422 is kept for a supervisor approving more than $100k and for self-approval.
- **D-43:** the reserve history entity is called `ReserveTransaction` in C# and maps to the `ReserveHistory` table (S15.3 says entities match table names). The spec calls these rows transactions, and names already differ by plurality elsewhere.
- **D-44:** reject is limited by the approver's amount authority (supervisors only up to $100,000, per S3). S10.2 says only "Requires Supervisor or Manager role" for reject, with no amount limit.
- **D-51:** ClaimStatusTransitions has no tenant column, and ClaimNumberSequences/IdempotencyRecords have no soft-delete or shadow audit columns. B A.4 and S15.1 ask for OrganisationId and audit columns on all tables, but these tables are global configuration or infrastructure, not business data.
- **D-67:** AutoMapper 14.0.0 is used with three known high-severity DoS advisories suppressed. The fix exists only in the commercial 15.1.4+/16.3+ lines. The "not affected" analysis rests on flat maps, ProjectTo for reads and no user-supplied object graphs, backed by a recursion-guard test. The upgrade path is 16.3+ under the Community licence.
- **D-72:** model-binding failures (malformed JSON, unknown enum names) return **422**, not ASP.NET's default 400, and an anonymous request to an unknown path gets **401**, not 404 (the bearer fallback policy covers every request).
